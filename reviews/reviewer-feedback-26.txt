Assuming sealed V3 looks like development, I think **V4 should be about the life cycle of abstractions, not about creating more expressive programs yet**.

V3 would have established the base case:

[
\text{private recurring computation}
\rightarrow
\text{PROMOTE}
\rightarrow
\text{shared abstraction}
\rightarrow
\text{cheaper future learning}.
]

But it also gives us the next problem almost for free: the learner creates roughly **5 abstractions for 2 real families**, and even the structureless control creates some abstractions. So birth works, but the library is messy.

The V4 question should be:

[
\boxed{
\textbf{Can a learner rationally maintain and reorganize its computational language as evidence changes?}
}
]

I'd call it something like **V4: The Life of an Abstraction** or **V4: The Economy of a Library**.

## The key conceptual shift

V3 treats promotion almost like a permanent decision:

[
\operatorname{PROMOTE}(A).
]

I think V4 should instead discover that abstraction creation is **speculative**.

A useful lifecycle is:

[
\boxed{
\text{birth}
\rightarrow
\text{usage}
\rightarrow
\text{consolidation}
\rightarrow
\begin{cases}
\text{retain}\
\text{merge}\
\text{fork}\
\text{delete}
\end{cases}}
]

This solves the refusal problem in a much more natural way than trying to make PROMOTE perfect.

You don't actually need:

[
P(\text{false birth})=0.
]

You need:

[
P(\text{false abstraction survives})\approx0.
]

That's a much more realistic objective.

# V4.1 should be MERGE + DELETE

I would make this the **core V4 experiment**.

Don't introduce nonstationarity immediately. Stay in the validated V3 world and ask whether the system can clean up after PROMOTE.

You already expect:

[
A_1,A_2,A_3
]

to sometimes be functionally redundant representations of the same underlying family.

Define:

[
A_i\sim_\epsilon A_j
]

when they are mutually substitutable on held-out functional probes.

Then allow:

[
\operatorname{MERGE}(A_i,A_j)\rightarrow A_{ij}.
]

The edit is accepted only if:

[
J_{\rm after}<J_{\rm before}.
]

Similarly, an abstraction that was created but subsequently receives little useful reuse gets a prospective retention value:

[
V_{\rm retain}(A)
=================

## \mathbb E[\text{future savings from }A]

D(A).
]

If:

[
V_{\rm retain}(A)<0,
]

allow:

[
\operatorname{DELETE}(A).
]

This directly tests the weakness V3 exposes.

The smoking-gun result would be:

[
\text{PROMOTE-only library size}\approx5
]

becoming something like:

[
\text{maintained effective library size}\approx2
]

in the structured world, while the structureless world's speculative library moves toward:

[
\approx0.
]

But importantly, **don't require recovery of the teacher's number two**. The primary outcome should be lower:

[
D_{\rm library}
+
D_{\rm references}
]

at equal or better predictive/future-learning performance.

# I think this should be the central V4 hypothesis

Something like:

> **H14 — Rational Library Maintenance.** When abstraction birth is imperfect, evidence from subsequent reuse allows a learner to consolidate functionally redundant abstractions and retire abstractions whose prospective value becomes negative, reducing total lifetime description and retrieval burden without sacrificing predictive performance or future-task adaptation.

The comparison should be:

[
\boxed{
\text{PROMOTE+MERGE+DELETE}
\quad\text{vs}\quad
\text{frozen V3 PROMOTE-only}.
}
]

That's beautifully causal.

V3 says birth is useful.

V4 asks whether managing the things you've created adds additional value.

# Then V4.2 should introduce FORK

Once retention/merging works, now let the world change.

Suppose abstraction (A) has become heavily shared:

[
A\rightarrow{\tau_1,\ldots,\tau_{50}}.
]

Then a new regime appears that wants:

[
A+\delta.
]

The naive learner can update (A):

[
A\leftarrow A+\delta.
]

But that changes all 50 old programs.

That's catastrophic forgetting through shared mutable state.

The natural solution is **copy-on-write**:

[
A
]

remains stable.

The new task starts with:

[
A+\delta_\tau.
]

If that deviation is one-off, leave it local.

If the same deviation appears repeatedly:

[
\delta_1\approx\delta_2\approx\delta_3,
]

then:

[
\boxed{
\operatorname{FORK}(A)\rightarrow A'
}
]

where:

[
A'\approx A+\delta.
]

Now old tasks reference (A), and the new regime references (A').

That is almost a perfect continual-learning mechanism.

# The FORK experiment could be extremely clean

Start with a V3 learner that has successfully promoted family (A).

Then halfway through the lifetime, split the environment:

[
A\rightarrow
\begin{cases}
A_1\
A_2
\end{cases}.
]

Compare three policies:

1. **Update-in-place:** modify (A).
2. **Never-update:** keep (A), use private residuals forever.
3. **Copy-on-write:** adapt privately first, FORK when recurrence earns it.

My strong prediction is:

[
\text{copy-on-write}
]

wins the lifetime objective.

Update-in-place should suffer old-task interference.

Never-update should retain too many private bits.

Copy-on-write should get:

[
\text{old behavior preserved}
+
\text{new-task adaptation}
+
\text{eventual compression}.
]

If that works, you've basically demonstrated a neural analogue of persistent data structures/version control.

# Then test hysteresis

This is one of the sharpest theoretical predictions in the whole project.

Creating an abstraction costs:

[
C_{\rm create}.
]

But retaining an already-existing abstraction costs only:

[
C_{\rm retain}.
]

Therefore:

[
C_{\rm create}>C_{\rm retain}.
]

So the recurrence level required to create an abstraction should be higher than the recurrence level at which an existing one becomes worth deleting:

[
\boxed{
r_{\rm create}>r_{\rm delete}.
}
]

That predicts a hysteresis loop.

Increase recurrence slowly:

```text
private
private
private
PROMOTE
shared
shared
```

Then decrease it:

```text
shared
shared
shared
shared
DELETE
private
```

The transition points shouldn't coincide.

If you actually observe that, it would provide very strong evidence for your interpretation of abstractions as **investments**.

That's much deeper than merely showing MERGE/DELETE work.

# V4 should make the environment nonstationary

V1–V3 mostly answer questions under a stationary recurrence structure.

V4 should change that:

[
r
\rightarrow
r(t).
]

Now the learner has to estimate:

[
P(\text{future reuse}\mid H_t).
]

That turns prospective value from a clever gate into a necessity.

An abstraction that was enormously useful yesterday may be worthless tomorrow.

A previously useless computation may suddenly recur constantly.

The computational language itself should track the environment.

That begins to look like actual continual learning.

# I would structure V4 as one ladder

1. **V4.1 — MERGE/DELETE:** Can reuse evidence clean up speculative births? This directly addresses V3's observed fragmentation and false promotions.
2. **V4.2 — FORK/copy-on-write:** Can the library adapt to regime splits without corrupting old programs?
3. **V4.3 — hysteresis:** Do CREATE and DELETE thresholds differ as predicted by abstraction-as-investment economics?
4. **V4.4 — priced retrieval, exploratory:** Start charging for an unnecessarily large library and ask whether lifecycle management reduces not only bits but search/indexing cost.

I would gate every rung on the previous one.

Don't implement the whole thing simultaneously.

## The larger theoretical model after V4

That's already a remarkably complete **continual computational-memory system**.

\text{repeated private bits}\Rightarrow\text{PROMOTE}

[
\text{fragmented births}\Rightarrow\text{MERGE}

For the actual **first V4 experiment**, though, I would be ruthless: **PROMOTE + MERGE + DELETE versus frozen V3 PROMOTE-only**. Make speculative birth + evidence-based survival work cleanly first. Then bring in nonstationarity and FORK.

# 2. Think of abstractions as **real options**

This is a direction I think could become theoretically rich.

An abstraction with no current use isn't necessarily worthless.

Maybe its regime will return.

So DELETE shouldn't ask:

> Has (A) been used recently?

It should ask:

> What is the expected value of keeping the option to reuse (A)?

That means:

[
V_{\rm retain}(A)
=================

P(\text{return})\times
\text{value if returned}
------------------------

D_{\rm retain}(A).
]

This gives you an excellent experiment.

### A → B → A world

First (A) is common.

Then it disappears.

Later either:

### Temporary dormancy

[
A\rightarrow B\rightarrow A.
]

or:

### Permanent disappearance

[
A\rightarrow B\rightarrow B\rightarrow\cdots
]

A good lifecycle learner should retain (A) through short expected dormancy but eventually delete it if evidence says the regime is gone.

That's a much deeper test than:

> delete unused stuff.

It makes long-term memory itself an economic decision.

# 3. Hysteresis needs one very important control

Your prediction:

[
r_{\rm create}>r_{\rm delete}
]

is excellent.

But there is a nasty confound.

Any slowly adapting dynamical system can show an apparent hysteresis loop simply because it **lags behind a changing environment**.

Increase recurrence:

[
r\uparrow
]

and promotion occurs late because learning takes time.

Decrease recurrence:

[
r\downarrow
]

and deletion occurs late for the same reason.

Voilà: fake hysteresis.

### The decisive test

Run several sweep rates:

[
v_1>v_2>v_3.
]

Measure:

[
r_{\rm create}(v)
]

and:

[
r_{\rm delete}(v).
]

If the loop is merely adaptation lag:

[
v\rightarrow0
\Rightarrow
r_{\rm create}-r_{\rm delete}\rightarrow0.
]

If the loop is genuinely economic:

[
v\rightarrow0
\Rightarrow
r_{\rm create}-r_{\rm delete}>0.
]

**I would preregister this.**

It makes H15 much more convincing.

# 4. Every edit needs to pay a migration cost

This is easy to miss.

Suppose:

[
A,B\rightarrow C.
]

MERGE doesn't merely cost:

[
D(C).
]

Every task referencing (A) or (B) may need its reference rewritten.

So:

[
C_{\rm merge}
=============

D(C)
+
D(\text{reference rewrites})
+
C_{\rm validation}
+
C_{\rm fitting}.
]

Likewise DELETE may require:

* removing table entries;
* rewriting references;
* restoring private residuals if something still depends on it.

FORK requires:

* storing (A');
* changing references for the diverging tasks.

If these edits are treated as free, lifecycle operations will look artificially attractive.

You don't necessarily need to charge all compute in V4.1, but **log every migration cost**.

# 5. This may force you to invent stable handles

There's an architectural consequence hiding there.

If tasks point directly to physical slot 7:

```text id="qayh2e"
task → slot 7
```

and you merge/delete/reorganize slots, references become expensive to rewrite.

Instead, you may want:

```text id="1vzj6b"
task → abstraction ID X37
              ↓
        current implementation
```

Then MERGE can do:

```text id="zrn8am"
X37 ─┐
     ├→ X91
X52 ─┘
```

with a small indirection table.

In other words, lifecycle management may naturally force the emergence of a **symbol table / stable addressing layer**.

That is extremely relevant to the full vision.

A computational language needs stable names.

# 8. FORK should be copy-on-write, not “split a module”

I feel quite strongly about this.

When evidence suggests a shared abstraction needs changing:

[
A\rightarrow A+\delta,
]

don't immediately decide whether to fork.

Start with:

[
\boxed{
A+\Delta_{\rm local}
}
]

for the new tasks.

That's copy-on-write.

Then if:

[
\Delta_1,\Delta_2,\Delta_3,\ldots
]

recur:

[
\operatorname{PROMOTE/FORK}(A,\Delta)
\rightarrow A'.
]

So FORK is really just **PROMOTE conditioned on an existing parent**.

This gives you:

[
A'
==

A+\Delta.
]

That's elegant because you don't need an entirely separate conceptual mechanism.

The library becomes genealogical:

```text id="wuzgvt"
       A
      / \
     /   \
   A'     A''
```

You may eventually discover useful **inheritance / delta encoding** between abstractions too:

[
D(A')=D(A)+D(\Delta)
]

rather than storing both independently.

That's another compression opportunity.

# 11. Frequency is not value

A subtle trap:

> retain the most frequently used abstractions.

An abstraction used twice might save:

[
10,000\text{ nats/use},
]

while one used 100 times saves:

[
5\text{ nats/use}.
]

So construct a matched experiment:

### A

frequent, low-value reuse.

### B

rare, high-value reuse.

A rational lifecycle should compare:

[
N_{\rm reuse}\times S_{\rm reuse}.
]

Not merely (N).

This would directly establish that the library is managing **economic value**, not popularity.

# 12. Give lifecycle operations matched refusal controls

Every operation should have its own “don't do it” world.

### DELETE

Abstraction temporarily dormant but scheduled to return.

Must retain.

### MERGE

Two abstractions superficially similar but behaviorally incompatible on held-out contexts.

Must refuse.

### FORK

Temporary noisy residual deviation.

Must not fork.

### RETAIN

Abstraction genuinely obsolete.

Must eventually delete.

This should become the V4 equivalent of V3's four-way audit.

# 13. Don't let edit order become a hidden hyperparameter

Suppose sleep sees:

```text id="ke8kli"
A ~ B
B ~ C
C low-use
```

Do you:

1. MERGE A+B, then reconsider C?
2. DELETE C, then MERGE?
3. MERGE all three?

Different operation order may produce different libraries.

You need a deterministic policy.

Perhaps:

[
\Delta J(e)
]

for every candidate edit (e).

At sleep:

1. generate candidates;
2. estimate (\Delta J);
3. apply the highest-value edit;
4. recompute;
5. repeat until no:

[
\Delta J>0.
]

That's basically greedy program refactoring.

Log the candidate queue.

Later you can ask whether global search improves it.

# 14. Avoid cascading distortion

[

You need something like a **semantic regression suite** for the library.

That's basically unit tests for learned abstractions.

Interesting analogy, but practically important.

New abstractions are cheap/speculative and monitored aggressively.

Long-lived/high-reuse abstractions move into a stable generation where deletion requires stronger evidence.

That naturally generates hysteresis!
