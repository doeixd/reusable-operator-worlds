## 1. The toy reveals a fundamental design principle

The result is much stronger than “Gaussian priors aren't tuned well”:

[
\begin{array}{c|cc}
&\text{unused}&\text{used}\
\hline
\text{Gaussian}&22.04&27.81\
\text{Gated}&0&16.10
\end{array}
]

The Gaussian code spends **79% of the used-task cost to say “do nothing.”**

That's structurally wrong for this project.

The natural null hypothesis for a new task should be:

[
\boxed{\text{reuse existing computation exactly}}
]

not:

[
\boxed{\text{sample a random perturbation around existing computation}.}
]

So I think you've discovered a constitutional requirement for the eventual architecture:

[
\boxed{
\textbf{zero information must correspond to the computational identity operation.}
}
]

That is bigger than V3.

For a task-specific residual:

[
\Delta_\tau=0
]

should be an exact representational state.

For future programs:

```text
no special case
no extra operation
no branch
no memory write
```

should likewise be true defaults.

New information should be encoded as **innovations from the default**, not as precision around a random variable.

# 2. I would probably replace Gaussian innovations with gated innovations

Something like:

[
\Delta_{\tau,k}
===============

g_{\tau,k}R_{\tau,k}
]

where:

[
g_{\tau,k}\in{0,1}.
]

Or even better, because your residuals already have meaningful rank:

[
r_{\tau,l}\in{0,1,2}.
]

Then:

[
r=0
]

means exactly:

[
R_\tau=0.
]

No task-specific computation.

Rank 1 means a small innovation.

Rank 2 means a more expensive innovation.

So the code naturally becomes:

[
D(R_\tau)
=========

D(r_\tau)
+
D(\theta_\tau\mid r_\tau).
]

Conceptually:

```text
REUSE
```

versus:

```text
SPECIALIZE rank=1 <payload>
```

versus:

```text
SPECIALIZE rank=2 <payload>
```

That is almost *already a primitive computational language*.

And promotion would transform repeated:

```text
SPECIALIZE <same-ish payload>
SPECIALIZE <same-ish payload>
SPECIALIZE <same-ish payload>
```

into:

```text
CALL A
CALL A
CALL A
```

That's exactly the V3 story.

# 3. One caution: make sure the toy's “0 bits” is honest

Before declaring the gated code superior by the precise 0-vs-22 number, make sure you're charging the **gate itself**.

If a decoder must distinguish:

[
g=0
]

from:

[
g=1,
]

that decision generally carries some information.

For a Bernoulli prior:

[
D(g=0)=-\log_2(1-\pi),
]

[
D(g=1)=-\log_2\pi.
]

So unused state need not literally cost zero.

However, under a sparse structural code you can encode only the **active indices**, so inactive coordinates can cost effectively almost nothing individually.

For example:

[
D=
D({\text{active positions}})
+
\sum_{\text{active }j}D(\theta_j).
]

That's perfectly legitimate.

So audit whether the toy includes:

* gate/presence bits;
* active-index bits;
* payload bits.

Even if the true unused cost becomes 0.1 or 1 bit instead of 0, the conclusion probably survives dramatically:

[
\sim1\ll22.
]

The important result is **exact identity semantics**, not literally zero metadata bits.

# 4. The replay audit needs one more step before changing the objective

This part is subtler.

You've measured an integrated KL coefficient range:

[
0.50\times\rightarrow3.38\times
]

with early tasks receiving ~3x the accumulated KL gradient of late tasks.

That is definitely worth understanding.

But repeated application of a regularizer during SGD is **not automatically equivalent to charging the description multiple times**.

Consider a static objective:

[
J_\tau
======

L_\tau+\beta KL_\tau.
]

If SGD visits that task ten times, it evaluates:

[
\nabla J_\tau
]

ten times.

That doesn't mean the final mathematical objective contains:

[
10\beta KL_\tau.
]

It can simply mean that task got ten optimization steps toward the same objective.

So the important audit isn't:

[
\text{total KL coefficient applied to task }\tau.
]

It's the **relative pressure of KL versus likelihood** for that task.

Compute something like:

[
R_\tau
======

\frac{
\text{integrated effective KL weight for }\tau
}{
\text{integrated effective data-likelihood weight for }\tau
}.
]

If:

[
R_\tau
]

is constant across task position, then the replay may be giving early tasks more optimization, but it's not necessarily changing their implied rate–distortion tradeoff.

If instead:

[
R_{\rm early}\gg R_{\rm late},
]

then you really do have a task-position-dependent coding penalty.

**That's the decisive audit.**

# 5. I would not simply stop charging KL during replay

Suppose task (\tau) completes.

Then later replay updates its task-specific state:

[
\mu_\tau\rightarrow\mu'_\tau.
]

If you no longer charge information cost during replay, the task could accumulate more and more retained information **for free**.

That would be wrong too.

So “pay KL only during initial acquisition” is coherent only if:

[
\boxed{\text{task-specific code freezes after acquisition}.}
]

Replay could still update:

[
\text{shared parameters}
]

but not:

[
\text{task code}.
]

That is actually an interesting design!

It creates a clean medium-timescale state:

```text
learn task code
     ↓
freeze task code
     ↓
replay consolidates shared substrate
```

But it changes the V2 learning protocol materially.

I'd treat it as an ablation, not silently adopt it.

---

# 6. There are therefore two clean solutions

### Option A — mutable task state

Replay is allowed to update task codes.

Then every replayed task update must preserve the intended ratio:

[
\frac{\text{code pressure}}
{\text{likelihood pressure}}.
]

Use importance weighting / per-task normalization so that this ratio does not depend on task age.

### Option B — acquisition then freeze

Task (\tau) gets its 128 examples.

Optimize:

[
L_\tau+\beta D_\tau.
]

Then freeze its task code.

Replay only updates shared structure.

This has a very attractive conceptual interpretation for your architecture:

[
\boxed{
\text{fast task acquisition}
\rightarrow
\text{medium-term frozen episode}
\rightarrow
\text{slow consolidation}.
}
]

I'd probably test both cheaply.

That fits V2 extraordinarily well.

The gated formulation asks the even sharper question:

[

with:

[
r_{\tau,l}\in{0,1,2}.

Now literal structure, information structure, and computational structure all agree.

That's much nicer.

# 11. This teaches us something about the eventual full architecture

This is why I find the toy surprisingly important.

In the eventual self-programming system, every representational extension should probably have a distinguished **null/default**.

For a residual:

[
\text{NONE}.
]

For a memory write:

[
\text{DON'T WRITE}.
]

For a branch:

[
\text{NO BRANCH}.
]

For an extra computation:

[
\text{HALT}.
]

For a new module:

[
\text{REUSE EXISTING}.
]

For a fork:

[
\text{DON'T FORK}.
]

New complexity should be represented as a sparse sequence of **departures from the default**.

That makes parsimony structural:

[
\boxed{
\text{existing computation is free/default;}
\quad
\text{novel computation has to earn its bits}.
}
]

That is probably exactly what you want in a continually learning model.

---

# 12. And the replay issue teaches a second general principle

Description cost is a property of **retained information**, not of how long that information has existed.

So:

[
\boxed{
\text{an old abstraction should not become more expensive merely because it has been replayed more times}.
}
]

Likewise in the eventual system:

* frequently retrieved memory shouldn't be “recharged” for storage;
* a program called 1,000 times pays storage once, execution 1,000 times;
* an abstraction retained for 10 years pays retention/storage, not re-description on every use.

So you should keep the currencies separate:

[
D=\text{persistent information}
]

[
C=\text{number/cost of uses}
]

[
L=\text{predictive error}.
]

That's going to matter hugely when you get to macros and loops.
