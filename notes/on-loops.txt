Yes — and I think **loops are actually an important missing piece** of the current formulation.

Right now ROW V1 is artificially limited to programs of fixed length 3:

[
P_4 \rightarrow P_1 \rightarrow P_6.
]

So the model can reuse an operator across tasks, but it does **not yet have a general mechanism for repeatedly calling an operator an arbitrary number of times**.

A more complete computational language should absolutely allow:

[
P_i,\quad P_i\circ P_i,\quad P_i^3,\quad \ldots
]

and, eventually, loops whose number of iterations depends on the input.

## The simplest version

Replace the fixed three-step executor with a recurrent shared workspace:

[
z_0=E(x)
]

and then repeatedly:

[
i_t = R(z_t, c_\tau)
]

[
z_{t+1}=P_{i_t}(z_t)
]

until:

[
R(z_t,c_\tau)=\text{HALT}.
]

Now the controller can produce:

```text
P7
P7
P7
P4
HALT
```

which literally means:

[
P_4(P_7(P_7(P_7(x)))).
]

The same primitive (P_7) is **called repeatedly**. No extra copy of its weights is needed.

That is already much closer to an actual program interpreter.

---

# And then loops fall out naturally

Suppose many tasks require:

[
P_7^n.
]

The naive route representation is:

```text
P7 P7 P7 P7 P7 P7 P7
```

But under an MDL objective, there is a shorter description:

```text
REPEAT 7 P7
```

So the abstraction system could discover a control primitive:

[
\operatorname{Repeat}(P,n).
]

Now program length changes from approximately:

[
n\log K
]

to:

[
\log K+\log n+\text{cost(REPEAT)}.
]

Once (n) gets large, the loop is overwhelmingly cheaper.

This is exactly the same compression logic we've been discussing.

**Loops are a compression primitive.**

# And this gives us a really clean experiment

We can extend ROW with tasks like:

[
T_1=P_2^2\circ P_5
]

[
T_2=P_2^4\circ P_1
]

[
T_3=P_2^7\circ P_6

without telling the learner that repeated (P_2) is special.

A sufficiently expressive learner could first represent them as:

```text
P2 P2 P5
P2 P2 P2 P2 P1
P2 P2 P2 P2 P2 P2 P2 P6
```

Then a compression/refactoring phase notices:

[
P_2,P_2,P_2,\ldots
]

and invents:

[
\boxed{\operatorname{Repeat}(P_2,n)}.
]

That's precisely the kind of **self-invented computational abstraction** that is more interesting than the current “reuse helps” result.

Because we didn't tell it:

> loops exist.

We gave it a computational substrate from which a loop representation could become economical.

# There are actually three levels of looping

### 1. Fixed repetition

```text
repeat 5:
    P7
```

or:

[
P_7^5.
]

This is easy and should be our first test.

The task-specific program has to infer (n).

---

### 2. Input-dependent repetition

Something like:

```text
while condition(z):
    z = P7(z)
```

Now the number of applications isn't stored in the task program.

It is determined by the evolving state:

[
z_t.
]

Controller:

[
h_t=R(z_t,c_\tau)
]

chooses either:

[
P_i
]

or:

[
\mathrm{HALT}.
]

For example:

[
P(\mathrm{HALT}\mid z_t)
]

can increase as some target condition is approached.

This lets the same learned program execute:

* 3 iterations for one input,
* 17 for another,
* 100 for another.

Now we've learned an **algorithm**, rather than a fixed unrolled computation.

---

### 3. Nested loops / recursion

Eventually:

```text
while A:
    P3
    while B:
        P8
```

or a learned macro calling itself.

That gets much harder, but conceptually the machinery is the same:

[
\boxed{
\text{workspace}
+
\text{callable primitives}
+
\text{controller}
+
\text{HALT}
}
]

gives you variable-depth computation.

---

# This matters enormously for our original LLM idea

Because this is exactly one place where a normal Transformer may be inefficient.

Imagine the useful computation is conceptually:

```text
while unresolved:
    refine_representation()
```

A fixed-depth Transformer instead has:

```text
layer_1_refinement
layer_2_refinement
layer_3_refinement
...
layer_48_refinement
```

with separately parameterized layers.

Even if those layers aren't literally identical, the model may be repeatedly approximating variants of the same transformation.

A recurrent callable primitive can instead store:

[
P_{\text{refine}}
]

once and execute:

[
P_{\text{refine}}^n.
]

So the comparison becomes:

[
\boxed{
\text{unrolled computation}
\quad\text{vs.}\quad
\text{stored algorithm + execution count}.
}
]

That's exactly the program-compression intuition we started with.

An MDL compiler might initially discover:

|z_{t+1}-z_t|<\epsilon.

# There are obvious failure modes

We'd have to prevent:

### Infinite loops

Put a maximum execution budget:

[
T_{\max}
]

and charge compute:

[
\mu T.

### Always running maximum depth

Again:

Prediction loss prevents that when further computation is needed.

Keep the controller deliberately small and include it in description-length accounting.

Shared (A).

### Temporal reuse

Call the same computation repeatedly:

[
A^n.

That's loops/recurrent computation.

Reuse a whole composition:

[
M=A\circ B\circ C
]

inside many larger programs.

Those are macros/subroutines.

A genuinely self-organizing computational language should eventually discover all three.

So perhaps the deeper architecture isn't merely a “primitive library.”

It's:

[
\boxed{

## But loops create an important experimental trap

Our current ROW teacher uses repeated bounded `tanh` residual transformations.

If we repeatedly execute the same operation:

[
P(P(P(\cdots P(x))))

it may converge toward a fixed point.

Then:

[
P^{10}(x)\approx P^{20}(x).
]

Now loop count becomes almost impossible to identify.

That's bad.

A learner might appear to generalize from 10 iterations to 50 simply because nothing meaningful happens after iteration 8.

So loop benchmarks need teacher operations whose repeated application remains behaviorally distinguishable.

We might want things such as:

### Controlled rotations

[

]

so:

[

]

actually depends meaningfully on (n).

### Permutation-like transformations

Repeated application cycles through states.

### Residual transformations close to identity

[
z_{t+1}=z_t+\epsilon f(z_t)
]

with carefully controlled stability.

### Discrete state transformations

Potentially easiest for loop experiments.

The crucial test is:

[
d(P^n,P^{n+k})
]

should remain substantial over the range we're testing.

Otherwise the benchmark is fake.

## There is another major ambiguity: loop vs exponentiated operator

Imagine the model learns a parameterized operation:

[
Q(x,n)
]

that directly computes approximately:

[
P^n(x).
]

That's not literally executing a loop.

But information-theoretically it might be **better**.

For a rotation, for example:

[
R_\theta^n=R_{n\theta}.
]

Executing (R_\theta) 1,000 times would be stupid if you can just compute:

[
R_{1000\theta}.
]

So we shouldn't assume:

> discovering a loop is always the best abstraction.

This is actually great for the research.

A smart system should be able to discover:

[
\boxed{
\text{interpret}
\quad\text{vs.}\quad
\text{compile}
}
]

depending on the operation.

For some (P):

[
P^n
]

can be efficiently compiled into a direct operation.

For others, there may be no cheap shortcut.

This starts brushing against **computational irreducibility**.

# That could become a really interesting distinction

Suppose we generate two families of repeated transformations.

### Reducible family

There exists a compact shortcut:

[
P^n(x)=Q(x,n).
]

### Irreducible-ish family

The best known way to compute:

[
P^n(x)
]

is approximately to execute (P) repeatedly.

Then a computationally intelligent learner should discover different representations.

For the reducible family:

```text
COMPILE(P, n)
```

For the irreducible family:

```text
REPEAT(P, n)
```

That's a much deeper question than “can an RNN loop?”

It's:

> **Can the learner discover the cheapest computational strategy for repeated structure?**

Suppose the learner encounters:

```text

A A A
A A A A A A A
```

Initially it represents literal traces.

[
\operatorname{Repeat}(A,n).

repeated across tasks.

That whole thing becomes:

[

And later:

So abstraction recursively creates a more powerful language:

[
\text{weights}
\rightarrow
\text{operators}
\rightarrow
\text{calls}
\rightarrow
\text{loops}
\rightarrow
\text{parameterized programs}
\rightarrow
\text{programs over programs}.

This is exactly what symbolic library-learning systems like DreamCoder exploit, except we'd be trying to do it over **learned neural transformations**.

This helps clarify the architecture.

### Execution system

A small neural VM:

[

Its job is simply to execute computations.

### Compression/compiler system

Looks at:

* functional equivalences;

It can propose:

# This also reconnects to the LLM scaling hypothesis more strongly

A conventional Transformer gives you:

[
L
]

fixed sequential layers.

Even if the same conceptual transformation is useful repeatedly, execution is largely represented by different layer parameters:

[
F_1,F_2,\ldots,F_L.
]

Our proposed system instead might learn:

[
\mathcal P={A,B,C,D,\ldots}
]

and run:

[
A\to B\to B\to B\to C\to HALT.
]

Then for another token/problem:

[
D\to A\to C\to HALT.
]

So **computation depth becomes independent of parameter depth**.

That is potentially a major architectural difference.

A 100-step reasoning process doesn't require 100 independently parameterized layers.

It can call a 20-operator library repeatedly.

## This creates a very sharp eventual scaling prediction

Imagine comparing models with equal stored parameters.

A fixed-depth Transformer has:

[
D_{\max}=L
]

sequential transformations before requiring another forward pass/system-level loop.

A recurrent operator machine has:

[
D_{\max}
]

determined mainly by compute budget.

So as problem complexity increases, perhaps the reusable machine can trade:

[
\text{more FLOPs}
]

for:

[
\text{less stored knowledge}.
]

That means scaling might have **two currencies**:

[
\boxed{
\text{parameters}
\quad\text{and}\quad
\text{runtime computation}.

Transformers lean heavily on the former.

Our hypothesis is that explicit reusable computation lets you substitute the latter for the former much more effectively.

That's quite interesting.

Calling (P) 100 times saves storage:

[

but costs:

[
100C(P).

A fused operation (Q\approx P^{100}) costs more storage:

Cheap memory / expensive compute:

This is literally the classic **time–space tradeoff**, appearing inside neural architecture learning.

Yes. A few things become clearer once loops are allowed, and some of them change what I think the architecture ultimately needs.

The biggest technical issue is **closure under repeated execution**. If a primitive (P) is learned only on states drawn from some distribution (z\sim D), then after one call you get (P(z)), after five calls (P^5(z)), and those later states may be far outside the distribution on which (P) was learned. So “reuse the same primitive repeatedly” only works if the shared workspace has a reasonably stable interface under composition. Recent depth-recurrent Transformer work explicitly needs stabilization mechanisms such as identity-biased recurrence and LayerScale to make deep reuse of one block work reliably. ([arXiv][1])

That makes our old **neural ABI** idea much more important. Every operator should satisfy something like

[
P_i:\mathcal Z\rightarrow\mathcal Z
]

where (\mathcal Z) has a persistent semantic/statistical contract. Otherwise the model learns `P7-after-P3-at-depth-4`, not a genuinely callable `P7`.

I think there are about six additional consequences:

1. **We must distinguish a loop from repeated unrolling.**
   `P P P P P` uses shared weights, but it hasn't discovered `REPEAT(P, 5)`. The latter is a higher-level abstraction because the execution trace itself is compressed.

2. **We need to distinguish interpretation from compilation.**
   Sometimes (P^{100}) genuinely requires ~100 sequential applications. Sometimes there's a shortcut (Q(x,100)). A good learner should be free to discover either:
   [
   \operatorname{REPEAT}(P,n)
   ]
   or
   [
   Q_n\approx P^n.
   ]
   That turns the objective into a genuine time-space tradeoff:
   [
   L=L_{\rm task}+\lambda D+\mu C.
   ]

3. **Variable computation isn't novel by itself.**
   Adaptive Computation Time already lets recurrent networks learn how many steps to execute, PonderNet learns probabilistic halting, and Universal Transformers reuse weights across depth with dynamic computation. ([arXiv][2]) Recent looped/depth-recurrent Transformer work pushes the same general idea further. ([arXiv][3])
   So our contribution cannot be “call a neural block repeatedly until HALT.”

4. **The interesting thing would be learning the *control abstractions themselves*.**
   Start with something primitive like:
   [
   {P_1,\ldots,P_K,\mathrm{HALT}}.
   ]
   Let wake-time learning produce traces:

   ```text
   P7 P7 P7 P4
   P7 P7 P7 P7 P4
   P7 P7 P4
   ```

   Then the sleep compiler might infer:
   [
   M(n)=[\operatorname{Repeat}(P_7,n),P_4].
   ]
   That is substantially different from merely putting a recurrent block in the architecture.

5. **Eventually you need state beyond one vector.**
   Real programs need temporary variables, branches, stacks, and memory. With only
   [
   z_{t+1}=P_i(z_t)
   ]
   you can do tail-recursive-style computation, but arbitrary nested calls eventually want something like:
   [
   (\text{workspace},\text{stack},\text{memory},\text{program counter}).
   ]
   I wouldn't implement that soon, but conceptually the endpoint is much closer to a learned VM than an MoE.

6. **Credit assignment becomes a serious optimization problem.**
   If an answer depends on 50 repeated neural calls, gradients must traverse all 50. The fact that recent depth-recurrent systems devote substantial architecture work to stabilizing 20+ recurrent steps is evidence that this is not trivial engineering. ([arXiv][1])

The fourth point is the one I find most interesting.

before attempting a learned compiler.

Current ROW can find a reusable primitive, but the result still lives within the same compositional depth as training.

With iteration we can train on:

[

[

If the system has merely memorized finite routes, this should break.

If it has represented:

[
\operatorname{Repeat}(P,n),

That is a much harder-to-fake demonstration of **algorithmic abstraction**.

We could even plot:

[
\text{maximum successful test iteration count}.
]

PonderNet already shows that adaptive computation can help extrapolation on synthetic tasks, so merely extrapolating via more recurrent steps isn't sufficient novelty either. ### Let the system choose whether to loop or compile

Give it both possibilities.

For each recurring repeated computation, compare:

[
\text{Program A: Repeat}(P,n)
]

against:

[
\text{Program B: learned fused operator }Q_n.
]

Under:

[
J=L+\lambda D+\mu C,
]

the learner should choose different solutions depending on memory/compute prices.

If (\lambda) is high and (\mu) low:

> reuse/loop.

If compute is expensive:

> compile/fuse.

You could literally sweep:

[
\frac{\lambda}{\mu}
]

and see whether learned neural organization crosses between **interpreter-like** and **compiled** representations.

That is a really interesting experiment because it stops asking “what architecture is best?” and instead asks:

[
\boxed{
\text{Does neural computational organization adapt rationally to the resource economics it is trained under?}
}
]

That connects MDL, loops, modularity, scaling, and self-refactoring in one place.

So I think the bigger picture is becoming:

[
\text{discover reusable transformations}
\rightarrow
\text{discover repeated execution}
\rightarrow
\text{compress traces into control abstractions}
\rightarrow
\text{choose interpretation vs compilation}
\rightarrow
\text{use the resulting language to make future learning cheaper}.
]

The first arrow is what ROW is testing now. The later arrows are where I think the genuinely non-obvious research starts.
